*   **`but 0 are available`**: This is the current state. The number of "available" pods (those that have passed their readiness probe) is 0.

Follow these steps in order. The first few are the most common culprits.

*   **`CrashLoopBackOff`**: The container started, crashed, and Kubernetes is trying to restart it. This is a very common issue.
*   **`ImagePullBackOff`**: Kubernetes couldn't pull the container image from the registry (e.g., Docker Hub, ECR, GCR).
*   **`Pending`**: The pod is waiting for a node to be scheduled on. If it stays in `Pending` for a long time, it's a scheduling issue.
*   **`ContainerCreating`**: The pod is being created. If it stays here, it's likely stuck pulling an image or creating a volume.

    3.  **Re-deploy**: Build a new Docker image with the fix and push it to your registry. Then, update your deployment to use the new image tag.

Kubernetes cannot download the container image.

*   **Symptom**: `ImagePullBackOff` status. Error in the `describe` events.
*   **Solutions**:
    1.  **Incorrect Image Name/Tag**: Double-check the `image:` field in your deployment's pod spec. Is the name spelled correctly? Is the tag correct (e.g., `v1.2.3` instead of `lates`)?

    3.  **Registry is Down**: Check if the container registry is accessible from your worker nodes.

*   **Symptom**: Pod status is `Running`, but `kubectl describe` shows `Liveness probe failed` or `Readiness probe failed`. The pod never becomes "Available".
*   **Solution**:
    1.  **Check the probe configuration**: Look at the `readinessProbe` in your deployment's container spec.
    2.  **Adjust the probe**:
        *   **Increase `initialDelaySeconds`**: Give your application more time to start up before the first probe check.
        *   **Increase `periodSeconds`**: Check less frequently.
        *   **Fix the probe logic**: Ensure the probe's HTTP endpoint (`/health`) or command is correctly implemented in your application and returns the right status code (e.g., 200 for success).

*   **Symptom**: Pod goes to `Running` and then quickly to `Terminated` with an `OOMKilled` (Out of Memory) message in the events.
*   **Solution**:
    1.  **Check resource limits**: Look at the `resources.requests` and `resources.limits` in your deployment's container spec.
    2.  **Increase the limits**: If your application legitimately needs more CPU or memory, increase the `limits`. You may also need to increase the `requests` to ensure it gets scheduled on a suitable node.

#### Cause 5: Scheduling Issues
The pod cannot be scheduled on any available node.

*   **Symptom**: Pod stays in `Pending` status indefinitely.
*   **Solution**:
    1.  **Check node resources**: Run `kubectl get nodes` to see if any nodes have available CPU/memory.
    2.  **Check taints and tolerations**: A node might have a "taint" that prevents pods from being scheduled on it unless they have a matching "toleration". Check your node taints with `kubectl describe node <node-name>` and ensure your pod spec has the correct tolerations if needed.
    3.  **Check node selectors/affinity**: Your deployment might have a `nodeSelector` or `affinity` rule that no node matches. Review your deployment manifest.

### What "OOMKilled" Means

*   **OOMKilled**: This stands for **Out-Of-Memory Killed**. It's not an error in your application code, but a direct action taken by the **Linux Kernel** (specifically, the OOM Killer).
*   **The Process**: The Linux Kernel manages the server's physical RAM. When the system runs out of memory and cannot free up any more, the OOM Killer is activated. It looks for processes that are consuming a large amount of memory and kills one or more of them to free up RAM and prevent the entire server from crashing.
*   **The Result**: In Kubernetes, a "process" is a container. When the OOM Killer kills a container, the Kubernetes control plane sees that the container has terminated unexpectedly and will typically restart it according to its `restartPolicy` (which is almost always `Always` for pods). This is why you might see your pod cycling between a "Running" and "CrashLoopBackOff" state.

---

### The Root Cause: Why Did the Container Run Out of Memory?

The container `payment-worker-6d8b2c-p3mnr` requested a certain amount of memory, but the application inside it tried to use more than that. This can happen for several reasons:

1.  **Memory Leak**: The most common cause. Your application code has a bug where it allocates memory but doesn't release it properly. Over time, its memory consumption grows until it hits the limit and is killed.
2.  **Insufficient Memory Request**: The container's `resources.requests.memory` (or the default limit) is simply too low for the workload it's handling. A sudden spike in traffic or data volume could push it over the edge.
3.  **Inefficient Data Processing**: The application might be loading a large dataset into memory all at once (e.g., reading a huge file, processing a massive API response, or holding a large result set from a database query) without streaming or processing it in chunks.
4.  **Third-Party Library Issues**: A library your application uses might have its own memory leak or be inefficient with memory management.

4: Node worker-3()
- Error: worker-3 has condition of type DiskPressure, reason KubeletHasNoDiskSpace: kubelet has disk pressure
Of course. This is a very common and critical issue in Kubernetes clusters. Let's break down what this error means, why it's a big problem, and how to systematically fix it.

---

### 1. What Does the Error Mean?

*   **`worker-3`**: This is the name of one of your worker nodes in the cluster.
*   **`DiskPressure`**: This is a **node condition**. Kubernetes sets this condition on a node when the kubelet (the agent running on the node) detects that the node's disk is under severe stress.
*   **`KubeletHasNoDiskSpace`**: This is the specific reason for the `DiskPressure` condition. It means the kubelet itself is running out of disk space.
*   **`kubelet has disk pressure`**: This is a human-readable summary. The kubelet has determined that the available disk space is critically low.

In simple terms: **The disk on your `worker-3` node is almost full, and the Kubernetes system has marked it as unhealthy and unable to accept new work.**

### 2. Why is This a Critical Problem?

When a node is in `DiskPressure`, the Kubernetes control plane will take several actions to protect the cluster:

1.  **Pod Scheduling**: The scheduler will **not** schedule any new pods onto this node. It's effectively quarantined from new work.
2.  **Eviction**: The kubelet will start **evicting** existing pods from the node to free up space. It prioritizes pods based on their Quality of Service (QoS) tier:
    *   **BestEffort** (evicted first)
    *   **Burstable**
    *   **Guaranteed** (evicted last, as they are considered the most critical)
3.  **Instability**: The node itself may become unstable. The kubelet, container runtime (Docker/Containerd), and other system processes can crash or malfunction when they run out of disk space, leading to a complete node failure.

### 3. How to Diagnose and Fix the Issue

Follow these steps in order. The goal is to first understand what is using the disk, then clean it up, and finally prevent it from happening again.

#### Step 1: SSH into the Problematic Node

Connect to the `worker-3` node via SSH.

```bash
ssh user@worker-3
```

#### Step 2: Check Disk Usage

Identify which partition is full. The most critical partition for this issue is usually `/var/lib/kubelet` or `/var/lib/docker`.

```bash
# See overall disk usage
df -h

# A more detailed view, including inodes (which can also fill up)
df -i
```

You will likely see that the `/` or `/var` partition is at or near 100% capacity.

#### Step 3: Find the Culprit (What's Filling the Disk?)

The space is almost certainly being consumed by one of these:
*   **Container Images**: Old, unused images.
*   **Container Log Files**: Uncontrolled logging that fills up the disk.
*   **EmptyDir Volumes**: Pods that have crashed but their `emptyDir` volumes are still mounted and holding data.
*   **Kubelet State**: Old pod sandboxes or other state that hasn't been cleaned up.

Let's investigate each one.

**A. Check Container Logs (Most Common Culprit)**

Logs are the #1 cause of disk pressure. Use `crictl` (the standard CRI tool) to find logs for containers that are using a lot of space.

```bash
# List all containers and their log sizes
crictl ps --no-headers -q | xargs -n 1 crictl inspect --output json | jq '.status.logPath' -r | xargs du -sh
```

This command will show you the size of each container's log file. Look for any that are several Gigabytes (GB) in size.

**To fix this:**
*   **Short-term**: Manually truncate the largest log files. **Be careful not to delete a file a process is writing to.** Truncating is safer.
    ```bash
    # Find the largest log file
    find /var/log/containers -name "*.log" -exec du -sh {} \; | sort -rh | head -n 5

    # Truncate the file (set its size to 0)
    sudo truncate -s 0 /var/log/containers/huge-log-file.log
    ```
*   **Long-term**: Configure log rotation for your containers. This is done via the Kubelet configuration. See the "Prevention" section below.

**B. Check Kubelet and Docker/Containerd Directories**

These directories can fill up with old data.

```bash
# Check the size of key directories
du -sh /var/lib/kubelet/
du -sh /var/lib/docker/  # If you use Docker
du -sh /var/lib/containerd/ # If you use containerd
```

**To fix this:**
*   **Clean up old images**: The kubelet has a built-in mechanism for this.
    ```bash
    # Force a garbage collection of unused images
    sudo crictl rmi --prune
    ```
*   **Clean up unused containers**: The kubelet should do this automatically, but you can force it.
    ```bash
    # Force a cleanup of 'dead' containers
    sudo crictl rmi --prune
    ```

**C. Check for Stuck `emptyDir` Volumes**

If a pod using an `emptyDir` volume crashes, the volume can persist and hold data until the pod is fully deleted.

```bash
# List all pods and their volumes
kubectl get pods --all-namespaces -o wide

# Find pods in a CrashLoop or other non-running state
kubectl get pods --all-namespaces | grep -E CrashLoopBackOff|ImagePullBackOff|ErrImagePull
```

If you find a problematic pod, delete it to reclaim the space from its `emptyDir`.

```bash
kubectl delete pod <pod-name> -n <namespace>
```

#### Step 4: Reclaim Space and Verify

After cleaning up the likely culprits, check the disk usage again.

```bash
df -h
```

You should see a significant amount of free space. The `DiskPressure` condition on the node will not clear immediately. The Kubernetes control plane needs to re-evaluate the node's status, which can take a few minutes. You can check the status from the control plane:

```bash
kubectl describe node worker-3
```

Look for the `Conditions` section. The `DiskPressure` status should change from `True` to `False`.

---

### 4. How to Prevent DiskPressure in the Future

Cleaning up is a temporary fix. You need to configure your cluster to manage disk space proactively.

#### 1. Configure Log Rotation (Most Important)

This is the most effective preventative measure. You need to tell the Kubelet how to manage logs.

Edit the Kubelet configuration file (location varies by OS; common paths are `/etc/kubernetes/kubelet.conf`, `/var/lib/kubelet/config.yaml`, or passed via `--config` flag).

Add or modify these settings:

```yaml
# Example Kubelet configuration
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
# ... other settings
serverTLSBootstrap: true
evictionHard:
  # ... other eviction thresholds
  nodefs.available: "10%"  # Evict if 10% of disk is free
  nodefs.inodesFree: "5%"   # Evict if 5% of inodes are free
imageGCHighThresholdPercent: 70  # Run GC when disk usage is > 70%
imageGCLowThresholdPercent: 50   # Stop GC when disk usage is < 50%
maximumDeadContainersPerPod: 3    # Keep a few dead containers for debugging
```

The key settings for logs are often controlled by the container runtime (Docker/Containerd). For Docker, you would configure its `log-opts`. For a more robust solution, use a dedicated logging sidecar like **Fluentd** or **Promtail**, which can be configured to ship logs to a central store (like Loki or Elasticsearch) and manage local log rotation.

#### 2. Set Eviction Thresholds

The `evictionHard` setting in the Kubelet config tells the kubelet *when* to start evicting pods to prevent a crash. The default thresholds might be too high. The example above is a good starting point.

#### 3. Implement Liveness and Readiness Probes

Probes help Kubernetes detect and restart unhealthy applications before they crash and leave behind large log files or stuck `emptyDir` volumes.

#### 4. Use Resource Requests and Limits

By setting resource requests and limits for your applications, you ensure they run on nodes with sufficient resources and prevent a single "noisy neighbor" from consuming all available disk space.

You need to install an Ingress Controller that uses the `nginx` class. The most common one is the **NGINX Ingress Controller**.

```bash
# Install the controller into the 'ingress-nginx' namespace

  --namespace ingress-nginx \
  --create-namespace
```

```bash
kubectl get pods -n ingress-nginx
```

You should see pods like `ingress-nginx-controller-...` in a `Running` state.

```bash
kubectl get ingressclass
```

The output should look something like this:

```yaml
# service.yaml

kind: Service

    - protocol: TCP
      port: 80       # The port the service will be available on
```
